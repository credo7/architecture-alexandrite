Выбор подхода к мониторингу
Гибридный подход с учетом специфики компонентов
1. RED метрики для API сервисов (Shop API, CRM API, MES API):

Rate - количество запросов в секунду
Errors - количество ошибок
Duration - время отклика

Обоснование: API сервисы - это точки взаимодействия с пользователями и партнерами. RED метрики дают четкое понимание пользовательского опыта.
2. USE метрики для инфраструктуры (серверы, базы данных):

Utilization - использование ресурсов
Saturation - степень насыщения
Errors - ошибки на уровне инфраструктуры

Обоснование: Инфраструктурные компоненты требуют мониторинга загрузки для планирования масштабирования.
3. Четыре золотых сигнала для критических бизнес-процессов:

Latency - время обработки заказов
Traffic - количество новых заказов
Errors - ошибки в бизнес-процессах
Saturation - загрузка системы обработки заказов

Обоснование: Бизнес-процессы требуют комплексного подхода для контроля SLA.
Выбор метрик для мониторинга
Критические метрики (P0 - мониторинг 24/7 с алертами)
API Сервисы - RED метрики:
3. Number of requests (RPS) for internet shop API

Зачем нужна: Мониторинг нагрузки от B2C клиентов, планирование масштабирования
Ярлыки: endpoint, method, status_code, user_type

5. Number of requests (RPS) for MES API

Зачем нужна: Критически важно после запуска API для партнеров, контроль B2B нагрузки
Ярлыки: endpoint, method, status_code, partner_id, api_version

19. Response time (latency) for shop API

Зачем нужна: Влияет на конверсию в онлайн-магазине
Ярлыки: endpoint, method, percentile (p50, p90, p99)

21. Response time (latency) for MES API

Зачем нужна: SLA для партнеров, критично для расчета стоимости
Ярлыки: endpoint, method, operation_type, percentile

28. Number of HTTP 500 for shop API
30. Number of HTTP 500 for MES API

Зачем нужны: Прямое влияние на потерю заказов и клиентов
Ярлыки: endpoint, error_type, method

RabbitMQ - критично для интеграции:
1. Number of dead-letter-exchange letters in RabbitMQ

Зачем нужна: Потерянные сообщения = потерянные заказы
Ярлыки: queue_name, exchange_name, routing_key, error_reason

2. Number of message in flight in RabbitMQ

Зачем нужна: Контроль очередей, предотвращение переполнения
Ярлыки: queue_name, consumer_tag, message_age

Важные метрики (P1 - ежедневный мониторинг с алертами по тренду)
Инфраструктура - USE метрики:
11. CPU % for MES API

Зачем нужна: MES API выполняет тяжелые расчеты, контроль производительности
Ярлыки: instance_id, region

14. Memory Utilisation for MES API

Зачем нужна: Расчет стоимости может потреблять много памяти
Ярлыки: instance_id, memory_type (heap, non-heap)

16. Memory Utilisation for MES db instance

Зачем нужна: База данных MES содержит сложные запросы для дашборда
Ярлыки: instance_id, db_name

18. Number of connections for MES db instance

Зачем нужна: Контроль connection pool, предотвращение исчерпания соединений
Ярлыки: db_name, connection_state, application_name

Дополнительные метрики:
4. Number of requests (RPS) for CRM API

Зачем нужна: Мониторинг нагрузки от менеджеров по продажам
Ярлыки: endpoint, method, user_role

20. Response time (latency) for CRM API

Зачем нужна: Производительность работы менеджеров
Ярлыки: endpoint, method, percentile

Зачем нужна: Контроль роста объема 3D файлов, планирование бюджета

24. Size of MES db instance

Зачем нужна: Планирование масштабирования базы данных

Кастомные бизнес-метрики
Время обработки заказа по статусам:

Зачем нужна: Контроль SLA в 3 недели, выявление узких мест
Ярлыки: order_status, order_complexity, percentile

Количество заказов в каждом статусе:

Зачем нужна: Выявление заторов в процессе обработки
Ярлыки: status, order_source (B2C, B2B API)

Среднее время расчета стоимости:

Зачем нужна: Оптимизация производительности расчетов
Ярлыки: model_complexity, polygon_count_bucket, calculation_method

Количество потерянных заказов:

Зачем нужна: Прямая метрика влияния на бизнес
Ярлыки: loss_reason, order_source, recovery_status

Рекомендации по настройке алертов
Критические алерты (немедленное реагирование):

HTTP 5xx errors > 1% от общего трафика за 5 минут
Response time p99 > 5 секунд для любого API
Dead letter queue > 0 сообщений
Messages in flight > 1000 для любой очереди
CPU > 80% в течение 10 минут
Memory > 85% в течение 5 минут

Предупреждающие алерты (реагирование в течение часа):

Response time p90 увеличилось на 50% относительно базовой линии
RPS снизился на 30% без видимых причин
Количество соединений к БД > 80% от максимума
Размер очередей растет стабильно в течение 30 минут

Информационные алерты (ежедневный обзор):

Заказы в статусе MANUFACTURING_STARTED > 72 часов
Среднее время расчета стоимости > 10 минут
Утилизация S3 storage увеличилась на 20% за неделю
