# Архитектурное решение по логированию

## Анализ системы и требования к логированию

### Системы для сбора логов

На основе C4-диаграммы и описания архитектуры компании необходимо собирать логи из следующих систем:

1. **Онлайн-магазин** (Vue + Java Spring Boot)
2. **CRM** (Vue + Java Spring Boot) 
3. **MES** (React + C#)
4. **RabbitMQ** (интеграционная шина)
5. **Базы данных** (PostgreSQL/MySQL на Yandex Cloud)

### Список необходимых логов с уровнем INFO

#### Онлайн-магазин:
- **Создание заказа**: timestamp, user_id, order_id, order_status = "INITIATED"
- **Загрузка файла**: timestamp, user_id, order_id, file_name, file_size, order_status = "FILE_UPLOADED"  
- **Отправка заказа**: timestamp, user_id, order_id, order_status = "SUBMITTED"
- **Аутентификация пользователя**: timestamp, user_id, ip_address, user_agent
- **API запросы**: timestamp, endpoint, method, response_code, response_time, user_id

#### CRM:
- **Подтверждение заказа**: timestamp, manager_id, order_id, order_status = "MANUFACTURING_APPROVED"
- **Закрытие заказа**: timestamp, manager_id, order_id, order_status = "CLOSED"
- **Действия менеджеров**: timestamp, manager_id, action_type, order_id

#### MES:
- **Расчет стоимости**: timestamp, order_id, calculation_time, polygon_count, calculated_price, order_status = "PRICE_CALCULATED"
- **Начало производства**: timestamp, operator_id, order_id, order_status = "MANUFACTURING_STARTED"
- **Завершение производства**: timestamp, operator_id, order_id, order_status = "MANUFACTURING_COMPLETED"
- **Упаковка**: timestamp, operator_id, order_id, order_status = "PACKAGING"
- **Отправка**: timestamp, operator_id, order_id, tracking_number, order_status = "SHIPPED"
- **Загрузка дашборда**: timestamp, operator_id, page_load_time, filters_applied

#### RabbitMQ:
- **Отправка сообщений**: timestamp, queue_name, message_id, source_system, target_system
- **Получение сообщений**: timestamp, queue_name, message_id, processing_time, status

#### Внешние API:
- **Входящие API запросы**: timestamp, client_id, endpoint, method, response_code, response_time
- **Исходящие запросы**: timestamp, target_service, endpoint, response_code, response_time

### Дополнительные уровни логирования

**WARNING** - для потенциальных проблем:
- Время расчета стоимости > 10 минут
- Загрузка дашборда MES > 5 секунд
- Ошибки валидации данных
- Повторные попытки обработки сообщений в RabbitMQ

**ERROR** - для критических ошибок:
- Сбои в расчете стоимости
- Ошибки интеграции между системами
- Недоступность баз данных
- Критические ошибки API

**DEBUG** - для детальной диагностики (только в dev/test):
- Детальная трассировка выполнения запросов
- Параметры входящих запросов
- SQL запросы и их время выполнения

## Мотивация

### Почему необходимо логирование

Компания «Александрит» сталкивается с критическими проблемами:
- Потеря крупных контрактов из-за проблем с заказами
- Жалобы клиентов на просроченные заказы
- Медленная загрузка MES дашборда
- Отсутствие visibility в процессах обработки заказов
- Длительное время разбора инцидентов

### Технические метрики, на которые повлияет логирование

1. **Время разрешения инцидентов** - сокращение с часов до минут
2. **MTTR (Mean Time To Recovery)** - уменьшение на 70-80%
3. **Скорость диагностики проблем** - от дней до минут
4. **Производительность систем** - выявление узких мест
5. **Качество интеграций** - мониторинг обмена сообщениями между системами

### Бизнес-метрики

1. **Удовлетворенность клиентов** - снижение количества жалоб на 60%
2. **Время обработки заказов** - оптимизация процессов на основе данных
3. **Эффективность операторов** - анализ производитель-ности работы
4. **Стоимость поддержки** - сокращение ресурсов на разбор проблем
5. **SLA соблюдение** - улучшение показателей доступности сервисов

### Приоритизация внедрения

**Первый этап (критический):**
1. **MES** - самые критичные проблемы с производством и дашбордом
2. **RabbitMQ** - интеграционная шина, влияющая на все процессы
3. **CRM** - управление заказами и взаимодействие с клиентами

**Второй этап:**
4. **Онлайн-магазин** - входная точка для B2C клиентов
5. **Внешние API** - для B2B партнеров

## Предлагаемое решение

### Архитектура системы логирования

```
┌─────────────────┐    ┌─────────────────┐    ┌─────────────────┐
│   Онлайн-       │    │      CRM        │    │      MES        │
│   магазин       │    │                 │    │                 │
│                 │    │                 │    │                 │
└─────────┬───────┘    └─────────┬───────┘    └─────────┬───────┘
          │                      │                      │
          │ Logs via             │ Logs via             │ Logs via
          │ Filebeat             │ Filebeat             │ Filebeat
          │                      │                      │
          ▼                      ▼                      ▼
┌─────────────────────────────────────────────────────────────────┐
│                    Logstash Cluster                             │
│                 (Processing & Filtering)                        │
└─────────────────────────┬───────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│                  Elasticsearch Cluster                         │
│                    (Storage & Indexing)                        │
└─────────────────────────┬───────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────────────────┐
│                       Kibana                                   │
│              (Visualization & Analytics)                       │
└─────────────────────────────────────────────────────────────────┘
```

### Технологический стек

**ELK Stack + Filebeat:**
- **Filebeat** - сбор логов с каждого сервера
- **Logstash** - обработка, фильтрация и обогащение логов
- **Elasticsearch** - хранение и индексирование
- **Kibana** - визуализация и анализ

**Альтернатива:** Grafana Loki + Promtail (более легковесное решение)

### Компоненты для внедрения

1. **На каждом сервере приложений:**
   - Filebeat agent для сбора логов
   - Настройка structured logging в приложениях

2. **Централизованная инфраструктура:**
   - Logstash кластер (2-3 узла для высокой доступности)
   - Elasticsearch кластер (3 узла minimum)
   - Kibana для визуализации
   - Alertmanager для уведомлений

3. **Обновления в приложениях:**
   - Стандартизация формата логов (JSON)
   - Добавление correlation ID для трейсинга
   - Конфигурация log levels

### Политика безопасности

**Доступ к логам:**
- **Полный доступ**: DevOps, архитектор, тимлид
- **Ограниченный доступ**: разработчики (только логи своих сервисов)
- **Только метрики**: продакт-менеджер, QA
- **Запрет доступа**: операторы, продавцы

**Обработка чувствительных данных:**
- Маскирование персональных данных (ФИО, телефоны, email)
- Хеширование идентификаторов пользователей
- Исключение из логов паролей, токенов, банковских данных
- Separate индексы для финансовых данных с повышенной защитой

**Аудит:**
- Логирование всех обращений к системе логов
- Ротация ключей доступа каждые 90 дней
- Регулярный аудит доступов

### Политика хранения логов

**Структура индексов:**
- `alexandrite-online-shop-YYYY.MM` - логи онлайн-магазина
- `alexandrite-crm-YYYY.MM` - логи CRM
- `alexandrite-mes-YYYY.MM` - логи MES  
- `alexandrite-integration-YYYY.MM` - логи RabbitMQ
- `alexandrite-api-YYYY.MM` - логи внешних API

**Retention policy:**
- **Hot tier** (0-7 дней): быстрый SSD, полнотекстовый поиск
- **Warm tier** (8-90 дней): более медленные диски, ограниченный поиск
- **Cold tier** (91-365 дней): архивное хранение, только агрегированные метрики
- **Удаление** после 365 дней (кроме критических инцидентов)

**Размеры:**
- Ожидаемый объем: ~50GB/день (все системы)
- Elasticsearch кластер: 10TB storage
- Retention: 1 год = ~18TB с учетом индексирования

## Система анализа логов

### Алертинг

**Критические алерты:**
- Время расчета стоимости > 30 минут
- Количество ERROR логов > 10/минуту
- Недоступность любой из систем > 2 минут
- Очередь RabbitMQ > 1000 сообщений
- Время загрузки MES дашборда > 10 секунд

**Warning алерты:**
- Увеличение времени отклика API > 2 секунд
- Рост количества WARNING логов > 50/минуту
- Аномальное количество новых заказов

**Каналы уведомлений:**
- **Критические**: SMS + звонок дежурному
- **Высокий приоритет**: Slack + email
- **Средний приоритет**: только Slack

### Обнаружение аномалий

**Machine Learning алгоритмы в Elasticsearch:**

1. **Anomaly Detection для объемов:**
   - Мониторинг количества заказов в час
   - Детекция DDoS атак по spike в API запросах
   - Выявление аномального поведения пользователей

2. **Pattern анализ:**
   - Нетипичные последовательности статусов заказов
   - Аномально долгие цепочки обработки
   - Паттерны ошибок в интеграциях

3. **Predictive алерты:**
   - Прогнозирование перегрузки систем
   - Раннее предупреждение о возможных сбоях
   - Capacity planning на основе трендов

### Дашборды и метрики

**Executive Dashboard:**
- Общее количество заказов по статусам
- SLA по времени обработки заказов
- Top-5 проблем за последние 24 часа
- Финансовые метрики (конверсия, средний чек)

**Operations Dashboard:**
- Производительность каждой системы
- Состояние интеграций
- Загрузка операторов и менеджеров
- Время отклика API

**Development Dashboard:**
- Errors/warnings по сервисам
- Performance метрики приложений
- Database slow queries
- Deployment статистика
